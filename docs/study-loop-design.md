# 学习闭环设计（设计对齐 v0.1）

> 目标：把「用户需求 → 完成学习」做成一个可运转、可追溯、数据驱动的闭环。
> 本文档只做设计对齐，不写代码。各环节功能、粒度、自动化程度待讨论。

## 1. 目标闭环（8 环节 + 收尾）

```
需求明确 → 方案制定 → 执行 → 检视验收 → 复习 → 数据分析 → 动态调整 → 完成判定 → 归档沉淀
```

每一环都要回答三个问题：
- 输入是什么？（数据来源）
- 产出是什么？（持久化到哪）
- 由谁驱动？（LLM 工具调用 / 规则 / 后台定时）

## 2. 现状盘点（基于代码核实，280 测试全绿）

| 环节 | 现状 | 已有实现 | 缺口 |
|------|------|---------|------|
| 需求明确 | 无独立环节 | — | 目标/起点/验收标准靠对话自由发挥，无结构化沉淀 |
| 方案制定 | 部分 | plan_create（标题/科目/目标/动机/节奏/截止/每日时长/里程碑），写入认知层 | 验收标准、复习策略、每日任务无结构化字段 |
| 执行 | 部分 | log_study_session（科目/分钟/笔记/关联计划）、today_minutes | 任务级完成无记录，只有时长 |
| 检视验收 | 部分 | plan_checkin（汇报+进度+下一步，追加决策记录） | 无验收证据（自测/习题/掌握度评分） |
| 复习 | 无 | 仅提醒（reminder） | 间隔重复、复习记录、复习效果全缺 |
| 数据分析 | 极少 | 进度三重推算、pace 节奏判断、今日时长 | 无趋势/达成率/复习稳定性/卡点识别 |
| 动态调整 | 部分 | plan_update + decision_log | 调整无数据依据，纯靠用户/LLM 主观 |
| 完成判定 | 无 | status 手动置 completed | 无证据驱动判定 |
| 归档沉淀 | 部分 | archive_plan | 无学习总结/认知沉淀 |

结论：现有实现覆盖「方案→执行→检视→调整」主干，**缺复习、缺数据分析、缺完成判定**，
且验收和调整都无证据支撑——闭环不完整，中间是断的。

## 3. 各环节功能设计（草案）

### 3.1 需求明确
- 输入：用户一句话诉求（如「三个月过英语四级」）
- 过程：LLM 对话内澄清——目标、期限、当前起点、每日可用时间、动机
- 产出：需求卡片字段写入 plan：`goal`（已有）+ 新增 `acceptance`（验收标准列表）+ `baseline`（起点评估）
- 驱动：LLM（对话内完成，不新增工具，扩展 plan_create 参数）

### 3.2 方案制定
- 输入：需求卡片
- 产出：计划落盘包含四件套——
  - `milestones`：阶段，每阶段带验收标准（现有只有 title/due_date/done）
  - `acceptance`：整体验收标准（可勾选）
  - `review_strategy`：复习策略（频率，如「每章学完 + 隔 1/3/7 天复习」）
  - `tasks`（可选）：周任务模板（内容/计划日期），粒度待讨论
- 驱动：LLM 生成 → 工具落盘；完整方案文档自动生成（补上之前「规划方案未落盘」的坑）

### 3.3 执行
- 输入：每日任务 + 用户汇报
- 产出：`log_study_session` 记录时长/笔记/关联计划（已有）；任务标记完成（新增 `task_done`）
- 驱动：LLM 工具调用；提醒（现有 reminder 机制）到点提示学习

### 3.4 检视验收
- 输入：按 cadence 定期检视
- 过程：checkin 升级为结构化——`progress_summary`（进展/卡点）+ 验收证据（自测结果、习题正确率）+ `mastery` 掌握度评分（1-5）
- 产出：`checkins[]` 追加记录（ts/摘要/证据/掌握度/下一步），替代现有纯文本 decision_log 的部分职能
- 驱动：LLM 引导用户自测 → 规则打分；里程碑完成自动更新进度

### 3.5 复习（新增环节）
- 对象粒度（待讨论）：材料 / 知识点 / 错题
- 数据：`review_items[]`（内容、next_review_at、interval、连续正确次数、最近结果）
- 算法：先上简化固定间隔（1/3/7/14/30 天），跑通后再考虑 SM-2
- 触发：到期复习提醒（复用 reminder）+ 复习打卡记录正确率
- 产出：复习记录写入 sessions 或独立 review_logs

### 3.6 数据分析（新增环节）
- 规则层（确定性强，先算）：
  - 时长趋势（近 7/30 天）
  - 里程碑达成率
  - 节奏 pace（已有）+ 停滞检测（连续 N 天无记录）
  - 复习稳定性（正确率变化、逾期复习数）
  - 科目/主题分布
- LLM 层：基于统计快照生成「分析报告 + 调整建议」（洞察归 LLM，数字归规则）
- 触发时机（待讨论）：每次 checkin 后自动 / 每周定时 / 用户主动
- 产出：`analysis_logs[]`（时间/统计快照/建议）

### 3.7 动态调整
- 输入：分析报告建议 + 用户确认
- 过程：plan_update 记录 `decision`（已有）+ 调整原因自动带出（来自分析）
- 决策点：建议自动应用 vs 用户确认后应用（默认：用户确认，安全优先）
- 产出：plan 字段变更 + decision_log 追加

### 3.8 完成判定（新增环节）
- 完成条件（规则预判）：验收项全部勾选 + 进度 ≥100% + 复习稳定（连续 N 次达标）+ 数据达标
- 过程：规则判定「建议完成」→ LLM 生成完成报告 → 用户确认 → status=completed
- 产出：`completion_report`（学到什么/数据回顾/经验）

### 3.9 归档沉淀（收尾）
- completed 计划归档时：生成学习总结 → 写入认知库（Note + Triple，沉淀为长期记忆）
- 复用现有 archive_plan + 认知写入逻辑

## 4. 数据模型变更（草案）

扩展 `study.json` 单文件，不拆库：
- `plans[].acceptance`：验收标准 [{title, done}]
- `plans[].checkins[]`：结构化检视记录（替代纯文本决策记录）
- `plans[].review_items[]`：复习项（内容/间隔/下次时间/连续正确/结果）
- `plans[].tasks[]`（可选）：任务模板（内容/计划日期/完成）
- `plans[].completion`：完成报告
- `analysis_logs`：分析历史（可与 plans 关联）

## 5. 待讨论决策点（需要你拍板）

1. **闭环环节是否完整**？还有没有漏的（如：中途放弃/失败处理、多计划并行、复盘仪式）？
2. **复习粒度**：材料级 / 知识点级 / 错题级？先做哪个？
3. **验收方式**：LLM 生成验收项 + 用户自测打分？还是里程碑完成即验收（更轻）？
4. **复习算法**：先简化固定间隔（1/3/7/14/30），还是直接 SM-2？
5. **调整方式**：分析建议自动应用，还是用户确认后应用？（默认用户确认）
6. **完成判定**：规则预判 + 用户确认，还是全自动？
7. **数据存储**：扩展 study.json 单文件，还是拆独立文件？
8. **本轮范围**：先做数据 + 工具闭环（电脑端验证），UI 后置？
